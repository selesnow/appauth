# appauth 0.3.0

Релиз с новыми возможностями. Существующие базы достраиваются миграцией при запуске (`aa_init_db()` или `aa_prepare_db()`), данные не меняются. Приложения, которые вызывают `aa_users_server()`, получают подтверждение удаления и две новые колонки в таблице; настройки по умолчанию остальное поведение не меняют.

* Даты создания и последнего входа. Миграция 6 добавляет в `users` колонки `created_at` и `last_login_at` (допускают пустое значение, у существующих пользователей они пустые: SQLite не разрешает значение по умолчанию `CURRENT_TIMESTAMP` при добавлении колонки). `aa_create_user()` и `aa_create_first_admin()` записывают `created_at`, модуль входа записывает `last_login_at` при успешном входе по паролю (в том числе после обязательной смены пароля и при создании первого администратора); вход по cookie автовхода дату не обновляет. `aa_get_user()` и `aa_list_users()` возвращают обе колонки (даты по UTC текстом `ГГГГ-ММ-ДД ЧЧ:ММ:СС`), `aa_users_overview()` добавляет колонки для показа `created` и `last_login` (местное время сервера, для неизвестных дат тексты «неизвестно» и «не входил»). Таблица пользователей в `aa_users_ui()` показывает колонки «Создан» и «Последний вход». Новые тексты `col_created`, `col_last_login`, `date_unknown`, `date_never`.
* Политика слабых паролей: настройка `password_policy` в `aa_settings()` (и в разделе `security` конфига). Слабым считается пароль из списка `aa_common_passwords()`, совпадающий с логином без учёта регистра или состоящий из одного повторяющегося символа. Режимы: `"off"` не проверять, `"warn"` (по умолчанию) принять пароль и показать предупреждение, `"reject"` отклонить пароль ошибкой `appauth_error_user` с причиной `password_common`, `password_equals_login` или `password_repeated`. В режиме `"warn"` модули показывают уведомление после добавления пользователя, сброса и смены пароля, при создании первого администратора и обязательной смене пароля и отправляют новое событие `weak_password_set` (значение: «логин: причина»). Для приложений со своим интерфейсом: `aa_weak_password_warning()`, а `aa_validate_password()` получила необязательный аргумент `login`. Существующие пароли не затрагиваются. Новые тексты `password_common`, `password_equals_login`, `password_repeated`, `weak_password_notice`.
* `aa_event_logger()`: готовый обработчик событий для `on_event`. Приложение задаёт только функцию записи `writer(action, user, session_id, value)`; пакет берёт на себя отбор событий (`events`, `actions`), переименование в названия действий журнала (`actions`), включение и выключение записи по событию (`enabled`, функция вызывается при каждом событии, поэтому изменения конфига действуют сразу) и преобразование значения (`format_value`). Опечатки в названиях событий ловятся сразу, сбой записи не прерывает действие пакета.
* Удаление пользователя в `aa_users_server()` требует подтверждения: кнопка «Удалить аккаунт» открывает окно с кнопками «Да, удалить» и «Отмена». Сервер удаляет только того пользователя, для которого показано окно, и только после нажатия кнопки подтверждения; подделанное или повторное подтверждение ничего не удаляет. Новые тексты `delete_confirm_title`, `delete_confirm_text`, `delete_confirm_button`, `button_cancel`. Идентификаторы для тестов: `delete_cancel`, `delete_confirm` (ID `delete` теперь только открывает окно).
* Каталог событий `aa_events()` дополнен событием `weak_password_set` (19 событий).
* Автотесты: 334 теста, 1598 проверок; браузерная проверка (`dev/e2e`) дополнена колонками дат, предупреждением о слабом пароле и подтверждением удаления.

# appauth 0.2.0

* `aa_auth_server()` возвращает функцию `logout_all(reload = TRUE)`: «выйти на всех устройствах» отзывает все токены пользователя, отправляет событие `sessions_revoked` и сразу выходит; открытые сессии на других устройствах закрывает `aa_session_guard()`. Перед вызовом приложение должно запросить подтверждение.

# appauth 0.1.0

* Первый релиз: пароли, защита входа, сессии, права, события, модули входа, пользователей и смены пароля, миграции схемы SQLite, документация и два пример-приложения. Подробности ниже.
* `RSQLite` перенесён из Suggests в Imports: пакет работает только с SQLite, и драйвер теперь ставится вместе с ним.
* Каркас пакета: структура папок, `DESCRIPTION`, лицензия, `.gitlab-ci.yml` с установкой в общую библиотеку сервера и уведомлениями в Telegram.
* Добавлена виньетка `architecture-and-security`: модель угроз, состав системы и данные, потоки (вход, первый запуск, автовход, выход, проверка прав, управление пользователями, старт приложения), гарантии, принятые решения и причины, известные ограничения, ответственность приложения, уроки найденных ошибок.
* Добавлены настройки и тексты:
    * `aa_settings()` - настройки авторизации (защита от подбора пароля, правила пароля, автовход, сроки хранения данных, роли), значения по умолчанию как в Server Manager;
    * `aa_settings_from_list()` - настройки из списка, например из раздела `config.yaml`;
    * `aa_texts()` - тексты интерфейса и сообщений на русском и английском с возможностью заменить любую строку, `aa_text()` - получить текст по ключу с подстановкой значений, `aa_text_keys()` - список ключей.
* Добавлена схема базы данных SQLite с версионными миграциями:
    * `aa_init_db()` - создать или достроить таблицы `users`, `auth_sessions`, `login_attempts` и служебную `appauth_migrations`, существующие данные не изменяются, повторный запуск ничего не меняет, распознаются старые схемы (в том числе таблица `users` без `id` и без `blocked`, пароли в открытом виде);
    * `aa_schema_version()` - версия схемы;
    * `aa_cleanup()` - удалить устаревшие попытки входа и токены;
    * `aa_prepare_db()` - подготовка базы при запуске приложения, которая не останавливает приложение при ошибке.
* Добавлена работа с паролями:
    * `aa_hash_password()` - хеш scrypt (пакет `sodium`) для хранения в базе, `aa_verify_password()` - проверка пароля по хешу (пароли в открытом виде, повреждённые хеши и сам хеш в качестве пароля никогда не проходят проверку, ошибок функция не бросает), `aa_is_password_hash()` - отличить хеш от открытого пароля;
    * `aa_validate_password()` и `aa_validate_login()` - проверка нового пароля и логина по правилам из `aa_settings()` (длина считается в символах), тексты ошибок на языке настроек;
    * `aa_migrate_plaintext_passwords()` - разовый перенос паролей из открытого вида в хеши с резервной копией, транзакцией, проверкой каждого хеша по исходному паролю и режимом `dry_run`, повторный запуск безопасен;
    * `aa_check_default_accounts()` и `aa_common_passwords()` - поиск учётных записей с паролем в открытом виде, паролем, совпадающим с логином, или распространённым слабым паролем.
* Добавлена работа с пользователями:
    * чтение: `aa_get_user()`, `aa_list_users()` (хеши паролей не возвращаются), `aa_users_exist()`;
    * создание: `aa_validate_new_user()` (проверка без создания, для показа ошибки в форме), `aa_create_user()`, `aa_create_first_admin()` (создаёт администратора одним SQL-запросом и только на пустой таблице, из двух одновременных запросов сработает один);
    * вход: `aa_authenticate()` (параметризованный запрос, логин сравнивается точно с учётом регистра, фиктивная проверка хеша для несуществующего логина выравнивает время ответа, открытые пароли и хеш в качестве пароля не принимаются);
    * действия: `aa_set_password()` (отзывает токены пользователя), `aa_set_role()`, `aa_set_blocked()` (блокировка отзывает токены), `aa_delete_user()` (удаляет токены и неудачные попытки входа, чтобы новый владелец такого же логина не получил доступ по чужой cookie);
    * проверки допустимости для интерфейса: `aa_check_can_block()`, `aa_check_can_delete()`, `aa_check_can_change_role()` возвращают текст причины или `NULL`.
    * При нарушении правил функции действий прерываются ошибкой класса `appauth_error_user` с текстом на языке настроек, в поле `reason` ключ причины.
* Правила пользователей: нельзя заблокировать или удалить самого себя, нельзя остаться без активного (не заблокированного) администратора ни блокировкой, ни удалением, ни сменой роли (сменой роли это правило добавлено сверх Server Manager), логин нового пользователя не может совпадать с существующим даже с точностью до регистра (в том числе кириллицей), существующие пары логинов вида `kiruka` и `Kiruka` сохраняются и работают как разные пользователи, логин не может начинаться или заканчиваться пробелом.
* Совместимость схемы проверена на копиях баз Server Manager (dev и prod): данные всех таблиц не изменяются, добавляется только служебная таблица `appauth_migrations`.
* Добавлена защита входа от подбора пароля:
    * `aa_record_attempt()` - записать попытку входа (успешная попытка обнуляет счётчик неудач этого логина);
    * `aa_login_lock_remaining()` - сколько секунд ещё действует блокировка логина после серии неудач;
    * `aa_global_throttled()` - общий лимит неудач в минуту по всему приложению;
    * `aa_clear_attempts()` - снять блокировку по попыткам;
    * `aa_login_gate()` - единая проверка перед входом: можно ли пробовать пароль, причина отказа и готовый текст (при сбое базы блокировки не применяются, на проверку пароля это не влияет);
    * `aa_users_overview()` - таблица пользователей с состоянием `ok`, `blocked` (вручную) или `locked` (по попыткам) и готовым статусом для интерфейса.
* Добавлены сессии и токены автовхода:
    * `aa_issue_token()` - выдать токен (32 случайных байта, в базе только sha256, срок `session_days`), не выдаётся при выключенном автовходе, для несуществующего и заблокированного пользователя;
    * `aa_find_session_user()` - пользователь по токену из cookie (токен должен быть не отозван, не истёк, пользователь не заблокирован, роль берётся из базы);
    * `aa_revoke_token()` - отозвать токен при выходе;
    * `aa_user_session_valid()` - периодическая проверка уже открытой сессии: блокировка, удаление и СМЕНА РОЛИ делают её недействительной сразу, а не при следующем входе (при сбое базы сессия сохраняется, `reason = "check_failed"`);
    * формат хранения совместим с Server Manager: уже выданные токены продолжают работать.
* Добавлены права доступа:
    * `aa_permissions_from_matrix()` - источник прав из матрицы «право -> роли» (как в Server Manager, роли вектором или одной строкой); матрицу можно передать функцией, тогда она читается при каждой проверке (редактор прав без перезапуска); роль администратора прав сама по себе не получает;
    * `aa_can()` - серверная проверка права, закрыта по умолчанию: нет пользователя, право не строка, источник прав упал или вернул мусор - `FALSE`; источник прав может быть любой функцией `function(user)` (права из базы, по группам);
    * `aa_require()` - первая строка обработчика: нет права - событие `access_denied` в хук `on_event`, уведомление пользователю и тихое прерывание обработчика; сломанный хук отказ не отменяет.
* Добавлены события авторизации: `aa_events()` - каталог из 16 событий (вход, блокировки, выход, принудительное завершение сессии, действия с пользователями, отказ в доступе) с описанием и содержимым поля `value`. Пакет сообщает о них единственному хуку `on_event(event, user, session_id, value)` и сам ничего не пишет в логи приложения; ошибка в хуке не прерывает действие; пароли и токены в события не попадают. Тест следит, чтобы каждое событие, отправляемое кодом пакета, было описано в каталоге.
* Добавлен интерфейс входа:
    * `aa_app_head()` - подключает CSS и JS пакета (стили формы и таблицы пользователей на переменных `--aa-*`, светлая тема классом `aa-theme-light`, cookie автовхода с `SameSite=Lax` и `Secure` на HTTPS, имя cookie настраивается, чтобы приложения на одном хосте не конфликтовали);
    * `aa_auth_ui()` и `aa_auth_server()` - модуль входа: форма входа или создания первого администратора на пустой базе, защита от подбора через `aa_login_gate()`, сообщение о блокировке администратором только при верном пароле, автовход по cookie, выход и принудительный выход; возвращает `user`, `logged_in`, `role` и `logout()`; о всех событиях сообщает хуку `on_event`.
* Добавлен модуль пользователей `aa_users_ui()` и `aa_users_server()`: таблица со статусами (подсветка заблокированных и временно заблокированных строк), карточка по двойному клику, добавление окном, смена роли, сброс пароля, блокировка и разблокировка, снятие блокировки входа, удаление. Управлять может только администратор, роль сверяется с базой при каждом действии; цель действия берётся из состояния открытой карточки, а не из браузера; правила (себя, последний администратор) проверяются на сервере. Слоты расширения карточки: `extra_card_ui(login, ns)` и `extra_card_server(input, output, session, login)`. В тексты добавлены ключи вкладки пользователей (ru и en).
* Модули проверены в настоящем браузере (Chrome и Playwright, сценарии в `dev/e2e`): вход, сообщения об ошибках, блокировка по попыткам, автовход по cookie и выход, карточка пользователя, подсветка заблокированных и временно заблокированных строк, светлая и тёмная тема, добавление пользователя; по итогам исправлено: форма входа занимает весь экран, сообщение об ошибке оформлено, при выходе не пишется ложное событие `access_denied`, новому пользователю по умолчанию предлагается роль без прав администратора.
* Добавлены помощники интеграции:
    * `aa_session_connection()` - подключение к SQLite, которое закрывается вместе с сессией Shiny (иначе подключение держит файл базы, и на Windows его нельзя переименовать или удалить), с необязательной подготовкой схемы;
    * `aa_session_guard()` - раз в `session_check_seconds` проверяет открытую сессию и завершает её, если пользователя заблокировали, удалили или сменили ему роль (событие `session_forced_logout` с причиной, токены отзываются, при сбое базы сессия сохраняется);
    * `aa_register_module()` - подключает серверную часть модуля один раз за сессию, когда у вошедшего пользователя появляется нужное право.
    * Отдельная функция `aa_logout()` не нужна: выход это `auth$logout()` из `aa_auth_server()`.
* Браузерная проверка (`dev/e2e`) дополнена: заблокированный администратором и пользователь со сменённой ролью при открытой сессии оказываются на форме входа в пределах интервала проверки, после повторного входа роль новая (33 проверки).
* Расширены автотесты: содержимое карточки пользователя (кнопки по состоянию пользователя, причины недоступности, слот, английский язык, свои тексты, экранирование логина с HTML), нестандартные настройки (свои роли и своя роль администратора в функциях и модулях), регрессионные проверки безопасности модулей (SQL-инъекции, огромные логин и пароль, хеш в качестве пароля), проверка, что каждое событие каталога реально отправляется кодом пакета; общие помощники тестов модулей вынесены в `helper-modules.R`.
* Добавлены смена собственного пароля и обязательная смена пароля:
    * миграция схемы 5: колонка `users.must_change`;
    * `aa_change_own_password()` - смена своего пароля с подтверждением текущего (токены остальных сессий отзываются, текущий остаётся, требование смены снимается);
    * `aa_set_password(must_change =, keep_token =)` и `aa_create_user(must_change =)` - пароль, который задал администратор, можно сделать временным; `aa_authenticate()` теперь возвращает ещё и колонку `must_change`;
    * модуль входа показывает форму смены пароля после верного временного пароля и не пускает в приложение до смены; токен по cookie для таких пользователей не работает;
    * `aa_password_ui()` и `aa_password_server()` - модуль смены собственного пароля (событие `password_changed`);
    * модуль пользователей: галочка «потребовать смену пароля» при добавлении и сбросе (по умолчанию включена), кнопка «Завершить все сессии» (`aa_revoke_sessions()`, событие `sessions_revoked`);
    * `aa_session_guard()` проверяет и токен сессии (`aa_user_session_valid(token =)`, причина `token_revoked`), поэтому сброс пароля и «завершить все сессии» завершают открытые сессии; раз в `cleanup_minutes` (60) сторож чистит устаревшие попытки входа и токены; `aa_auth_server()` возвращает ещё и функцию `token()`.
