# appauth 0.9.0

Релиз с новой возможностью: в пакет встроены навыки для ИИ-агентов (Claude Code, Codex, Posit Assistant и других). Поведение существующих функций, схема базы и настройки не меняются.

* Два навыка на английском языке лежат в `inst/skills`: `appauth` (справочник функций, схема базы, события, идентификаторы интерфейса) и `appauth-secure-shiny` (внедрение `appauth`, перенос самописной авторизации, вход через Google, аудит безопасности, шаблоны приложений, скрипты `audit_shiny_app.R` и `scaffold_auth.R`).

# appauth 0.8.0

Релиз с новой возможностью: пакет работает не только с SQLite, но и с DuckDB, MySQL / MariaDB и PostgreSQL. SQLite остаётся базой по умолчанию, формат данных и схема в ней не меняются, поэтому существующие приложения и работающие базы (включая Server Manager) продолжают работать без правок.

* Поддерживаемые базы определяются по подключению DBI: `RSQLite` (SQLite), `duckdb`, `RMariaDB` (MySQL и MariaDB), `RPostgres` (PostgreSQL). Драйверы ставятся отдельно и указаны в `Suggests`. Остальные базы отклоняются понятной ошибкой класса `appauth_error_connection`. BigQuery не поддерживается намеренно: в нём нет уникальных ограничений и атомарных обновлений, на которых держатся одноразовые токены (сброс пароля, вход через Google, резервные коды 2FA) и защита последнего администратора.
* Различия баз собраны в одном месте, `R/dialect.R`: определение диалекта, типы колонок, автоинкремент, создание индексов, вставка «если нет» и блокировка на время миграций. Остальной код пишет обычный SQL.
* Время теперь считает R и передаёт параметром (строка по UTC `ГГГГ-ММ-ДД ЧЧ:ММ:СС`, тот же формат, что хранил SQLite), поэтому в запросах нет `datetime('now')` и подобного. Побочный плюс: сроки жизни токенов не зависят от часов и часового пояса сервера базы. Время хранится текстом во всех базах, сравнение дат одинаково везде.
* Плейсхолдеры запросов подставляются под базу (`$1, $2` для PostgreSQL), числа `integer64` из `COUNT(*)` приводятся к обычным.
* Схема: новые базы SQLite создаются как прежде (имена таблиц, колонок и номера миграций те же). В MySQL колонки логинов, ролей и хешей создаются с двоичной collation без игнорирования пробелов в конце (`utf8mb4_0900_bin`, в MariaDB `utf8mb4_nopad_bin`), чтобы `Alsey` и `alsey` оставались разными логинами, как в SQLite. Уникальность email во всех базах обеспечивает обычный уникальный индекс (несколько `NULL` допустимы). В DuckDB таблица `users` создаётся сразу со всеми колонками: эта база не позволяет менять таблицу, на которую уже есть индекс.
* Миграции в MySQL и PostgreSQL выполняются под блокировкой (`GET_LOCK`, `pg_advisory_xact_lock`): одновременный старт нескольких экземпляров приложения безопасен. В MySQL DDL нельзя откатить, поэтому при обрыве миграции повторный запуск достраивает недостающее (миграции идемпотентны, как и раньше).
* `aa_session_connection()` получила аргумент `connect`: функцию без аргументов, которая открывает подключение к любой поддерживаемой базе (`db_path` для неё не нужен). Подключение закрывается вместе с сессией Shiny.
* Обёртки `aa_query()` и `aa_execute()` и проверка `aa_check_conn()` (вместо `aa_check_sqlite()`) внутренние. Публичные функции принимают подключение к любой поддерживаемой базе. Перенос открытых паролей в хеши `aa_migrate_plain_passwords()` работает по файлу и остаётся только для SQLite.
* Разное: порядок пользователей «по добавлению» берётся из `id` (а при его отсутствии из `rowid` в SQLite или из логина), время неудачи для блокировки считается в R.
* Проверка баз: полный набор тестов пройден на SQLite, DuckDB 2.0, MySQL 8.0 и PostgreSQL 16.4 (на MariaDB не запускался). Запуск на нужной базе: `Rscript dev/run-tests-db.R sqlite|duckdb|mysql|postgres`.
* Автотесты: весь набор можно запустить на любой поддерживаемой базе (`Rscript dev/run-tests-db.R sqlite|duckdb|mysql|postgres`). Тесты старых схем Server Manager и рекрутинга и файловый перенос паролей идут только на SQLite.

# appauth 0.7.1

Небольшое исправление входа через Google. Схема базы и настройки не меняются, существующие приложения продолжают работать без правок.

* Вход через Google теперь работает и со страницы на другом адресе, чем `google_redirect_uri`. Раньше при открытом по IP приложении (а возврат настроен на домен) вход заканчивался отказом `bad_browser`: `state` лежит в cookie адреса сайта, а cookie по IP и по домену разные. Теперь кнопка «Войти через Google» на таком адресе переводит на адрес возврата, и вход там запускается сам (параметр `?google=1`, без второго клика). Переход разрешён только на Google и на адрес из `google_redirect_uri`. Вход по паролю и автовход по cookie на каждом адресе работают независимо, как и раньше.
* Автотесты: проверены разбор адреса и сравнение адресов, переход с другого адреса, автозапуск по `?google=1` без бесконечного перехода, обычный запуск на адресе возврата.

# appauth 0.7.0

Релиз с новой возможностью: вход через Google (OpenID Connect) и возможность отключить вход по паролю. Выключено по умолчанию (`google_enabled = FALSE`, `password_login = TRUE`), поэтому приложения, которые это не включают, ведут себя как раньше. Существующие базы достраиваются миграцией 9 при запуске (`aa_init_db()` или `aa_prepare_db()`), данные не меняются. Новые зависимости `httr2`, `jose` и `jsonlite`.

* Вход через Google (authorization code flow с PKCE). Настройки `aa_settings()`: `google_enabled`, `google_client_id`, `google_client_secret`, `google_redirect_uri`, `google_domains`; все они читаются и из раздела `security` конфига. Включение без идентификатора, секрета или адреса возврата даёт ошибку сразу, секрет в `print()` настроек не попадает. На форме входа появляется кнопка «Войти через Google» (вместе с формой пароля или вместо неё).
* Кто может войти. Только пользователь, который уже есть в базе и у которого указан email, равный адресу Google-аккаунта: новых пользователей вход не создаёт, роль берётся из базы, заблокированный пользователь не входит. Список допустимых доменов организации `google_domains` проверяется по подписанному токену (поле `hd` с основным доменом организации Workspace, и домен email тоже должен быть в списке: если у организации есть вторичные домены, укажите в списке и основной, и вторичные); пустой список отключает проверку домена, тогда решает совпадение email. Двухфакторный код приложения при входе через Google не спрашивается (подтверждение делает Google).
* Правила безопасности. `state`, `nonce` и PKCE-проверка одноразовые и живут 10 минут (в базе `state` только в виде sha256). `state` из адреса сверяется с коротким cookie того браузера, который начал вход: чужую ссылку возврата в другой браузер подсунуть нельзя. Секрет клиента не покидает сервер. Токен Google проверяется целиком: подпись по ключам Google (только RS256, ключи кешируются на час), издатель, аудитория (с `azp` при нескольких), срок, `nonce`, подтверждённый email и домен. Разбор токена не использует частичное совпадение имён полей. Общий лимит запусков входа в минуту защищает таблицу от засорения. Пользователю при любом отказе показывается общий текст, причина (и email) попадает только в событие.
* Отключение пароля: `password_login = FALSE` скрывает форму пароля и «Забыли пароль?», а попытки входа по паролю и ссылки восстановления отклоняются на сервере, а не только в интерфейсе. Отключить пароль можно только вместе с `google_enabled = TRUE`: иначе `aa_settings()` бросает ошибку. Создание первого администратора на пустой базе остаётся.
* Миграция 9 добавляет таблицу `oauth_states` (параметры входа через Google). `aa_cleanup()` удаляет старые записи и возвращает четвёртое поле `oauth_states`.
* Каталог событий `aa_events()` дополнен событием `google_login_failed` (причина и email в `value`), у `login_success` значение `google`, у `login_failed` значение `password_disabled` (29 событий). Новые тексты интерфейса на русском и английском (ключи `google_*` и `password_login_disabled`).
* Исправлено оформление формы входа: поля ввода были уже кнопки и прижаты влево (Shiny задаёт им ширину 300 px, а карточка шире), теперь поля и кнопки одной ширины.
* Документация: описание потока, модель угроз и ограничения в `architecture-and-security`, рецепт и настройка OAuth-клиента в `extension-points`, README.
* Автотесты: 2329 проверок (новый файл `test-google.R`: настройки, подпись и содержимое токена, подмена алгоритма, чужой ключ, домены, одноразовый `state`, проверка браузера, отсутствие автосоздания пользователей, модуль входа; тесты схемы обновлены под версию 9). Разбор ключей проверен на настоящих публичных ключах Google.

# appauth 0.6.0

Релиз с небольшими удобствами для администратора и пользователя. Схема базы не меняется, миграций нет, существующие приложения продолжают работать без правок.

* Кнопки копирования в модуле двухфакторной аутентификации: рядом с ключом для ручного ввода и под резервными кодами появилась кнопка «Копировать» (в английском интерфейсе «Copy»). Ключ копируется без пробелов, резервные коды по одному в строке. По HTTPS используется буфер обмена браузера, иначе (и внутри окон Bootstrap) копирование идёт через скрытое поле. Кнопка копирует то, что уже видно на странице, поэтому ничего нового не раскрывает. Текст кнопки и подтверждения «Скопировано» задаются ключами `copy_button` и `copy_done`.
* Таблица пользователей в `aa_users_server()` получила колонки «Email» (галочка, если для восстановления пароля указан адрес; сам адрес в таблицу не попадает), «2FA» (галочка, если защита включена; колонка показывается только когда в настройках `totp_enabled = TRUE`) и «Автовходов» (число действующих токенов автовхода: на стольких устройствах вход запомнен). Ключи текстов `col_email`, `col_totp`, `col_autologins`, подсказка под таблицей дополнена пояснением про автовходы.
* Новая функция `aa_active_autologins(conn, login = NULL)`: число действующих (не отозванных и не истёкших) токенов автовхода пользователя или таблица по всем пользователям. Если таблицы токенов нет, возвращается ноль.
* `aa_users_overview()` отдаёт три новые колонки: `has_email`, `totp_on` и `autologins`. Колонки только добавляются, прежние остались на своих местах и не изменили значения. Для старой схемы без `email` и `totp_enabled` признаки равны нулю.
* Автотесты: проверены подсчёт автовходов (отозванные и истёкшие не считаются, регистр логина, отсутствие таблицы), новые колонки сводки и таблицы (включая старую схему и выключенную 2FA), кнопки копирования ключа и резервных кодов, тексты на двух языках.

# appauth 0.5.0

Релиз с новой возможностью: двухфакторная аутентификация (TOTP). Выключена по умолчанию (`totp_enabled = FALSE`) и добровольная, поэтому приложения, которые не включают её, ведут себя как раньше. Существующие базы достраиваются миграцией 8 при запуске (`aa_init_db()` или `aa_prepare_db()`), данные не меняются, у существующих пользователей защита выключена.

* Двухфакторная аутентификация по одноразовым кодам TOTP (RFC 6238, HMAC-SHA1, 6 цифр, шаг 30 секунд): пользователь сам включает её в блоке личного кабинета, после верного пароля вводит код из приложения-аутентификатора или резервный код. Алгоритм написан в пакете без новых зависимостей и проверен эталонными векторами RFC 4226 и 6238.
* Настройки `aa_settings()`: `totp_enabled`, `totp_key` (ключ шифрования секретов, строка не короче 16 символов, хранить вне базы), `totp_issuer` (название в приложении-аутентификаторе) и `totp_window` (допустимое расхождение часов в шагах, по умолчанию 1). Включение без ключа даёт ошибку сразу, ключ в `print()` настроек не попадает.
* Миграция 8 добавляет в `users` колонки `totp_secret` (секрет в зашифрованном виде), `totp_enabled` и `totp_last_step`, а также таблицу `totp_recovery` (в базе только sha256 резервных кодов).
* Новые функции: `aa_totp_setup()`, `aa_totp_enable()`, `aa_totp_disable()`, `aa_totp_enabled()`, `aa_verify_second_factor()`, `aa_recovery_codes_left()`, `aa_totp_secret()`, `aa_totp_uri()` и `aa_totp_code()`. Модуль `aa_totp_ui()` и `aa_totp_server()`: подключение (QR-код, ключ для ручного ввода, 10 резервных кодов один раз) и выключение (нужны пароль и код). QR-код строит необязательный пакет `qrcode` (в Suggests), без него показывается только ключ для ручного ввода.
* Правила безопасности. Секрет шифруется (sodium) ключом `totp_key`, одной базы для получения кодов недостаточно. Код принимается один раз: принятый шаг времени запоминается атомарным запросом. Резервные коды одноразовые. Неверный код считается неудачной попыткой входа, и логин блокируется по тем же правилам, что и при переборе пароля; успешная попытка входа записывается только после верного кода, поэтому правильный пароль не обнуляет счётчик. До кода токен автовхода не выдаётся. Восстановление пароля по email 2FA не обходит. При включении 2FA остальные сессии пользователя завершаются. Код при выключении проверяется только при верном пароле, чужая попытка не тратит резервные коды.
* `aa_auth_server()`: после верного пароля показывается форма кода (порядок: пароль, код, обязательная смена пароля, вход). Вход по cookie автовхода код не спрашивает.
* `aa_users_server()`: в карточке пользователя статус 2FA и кнопка «Сбросить 2FA» на случай потери телефона (секрет и резервные коды стираются, сессии пользователя завершаются, событие `totp_reset`). Удаление пользователя удаляет его резервные коды.
* Каталог событий `aa_events()` дополнен событиями `totp_enabled`, `totp_disabled`, `totp_failed`, `totp_reset` и `recovery_code_used` (28 событий). Новые тексты интерфейса на русском и английском (ключи `totp_*`, `card_totp`, `done_totp_*`).
* Пример `custom-permissions-app` показывает 2FA на вкладке Profile.
* Документация: описание потока, модель угроз, решения и ограничения в `architecture-and-security`, рецепт и параметры в `extension-points`, ключ и время сервера в `deployment`, шаг для существующих приложений в `integrating-existing-app`, README.
* Автотесты: 398 тестов, 2092 проверки (новый файл `test-totp.R`, обновлены тесты схемы под версию 8); браузерная проверка пройдена: подключение с QR-кодом и резервными кодами, вход с кодом, повтор кода и резервного кода, блокировка при переборе, сброс администратором.

# appauth 0.4.0

Релиз с новой возможностью: восстановление пароля по email. Выключено по умолчанию (`reset_enabled = FALSE`), поэтому приложения, которые не включают его, ведут себя как раньше. Существующие базы достраиваются миграцией 7 при запуске (`aa_init_db()` или `aa_prepare_db()`), данные не меняются.

* Восстановление пароля по email. Настройки `aa_settings()`: `reset_enabled`, `send_reset` (функция `function(email, link, login)`, отправляет письмо, например через `emayili`), `reset_base_url` (адрес приложения, к нему добавляется `?reset=<токен>`), `reset_ttl_minutes` (60), `reset_max_per_hour` (3) и `reset_max_per_minute` (10); все они читаются и из раздела `security` конфига. Включение без `send_reset` или `reset_base_url` даёт ошибку сразу.
* Миграция 7 добавляет колонку `users.email` (допускает пустое значение, у существующих пользователей пустая; адрес хранится в нижнем регистре, уникальность действует только для заданных адресов) и таблицу `password_resets` (в базе только sha256 токена, срок жизни, признак использования).
* Новые функции: `aa_set_email()`, `aa_get_email()`, `aa_request_password_reset()`, `aa_reset_token_login()` и `aa_reset_password_with_token()`. `aa_create_user()` получила аргумент `email`.
* Правила безопасности. Ответ формы всегда один и тот же, найден ли пользователь, есть ли у него адрес, заблокирован ли он; причина попадает только в событие. Токен 256 бит, одноразовый, новый запрос гасит прежние ссылки, слабый пароль токен не тратит, из двух одновременных запросов сработает один. Лимиты писем на пользователя в час и общий в минуту. После смены пароля по ссылке отзываются все токены автовхода, гасятся остальные ссылки, снимаются блокировка по попыткам и требование смены пароля. Заблокированному пользователю письмо не уходит, ссылка заблокированного не работает. Сброс пароля администратором, смена пароля и удаление пользователя гасят неиспользованные ссылки.
* Модуль `aa_auth_server()`: ссылка «Забыли пароль?» на форме входа, форма запроса ссылки, чтение параметра `reset` из адресной строки (параметр сразу убирается из адреса) и форма нового пароля. После смены пароля пользователь входит обычным путём. Модуль `aa_users_server()`: поле email в карточке пользователя и в окне добавления.

Релиз с новыми возможностями. Существующие базы достраиваются миграцией при запуске (`aa_init_db()` или `aa_prepare_db()`), данные не меняются. Приложения, которые вызывают `aa_users_server()`, получают подтверждение удаления и две новые колонки в таблице; настройки по умолчанию остальное поведение не меняют.

* Даты создания и последнего входа. Миграция 6 добавляет в `users` колонки `created_at` и `last_login_at` (допускают пустое значение, у существующих пользователей они пустые: SQLite не разрешает значение по умолчанию `CURRENT_TIMESTAMP` при добавлении колонки). `aa_create_user()` и `aa_create_first_admin()` записывают `created_at`, модуль входа записывает `last_login_at` при успешном входе по паролю (в том числе после обязательной смены пароля и при создании первого администратора); вход по cookie автовхода дату не обновляет. `aa_get_user()` и `aa_list_users()` возвращают обе колонки (даты по UTC текстом `ГГГГ-ММ-ДД ЧЧ:ММ:СС`), `aa_users_overview()` добавляет колонки для показа `created` и `last_login` (местное время сервера, для неизвестных дат тексты «неизвестно» и «не входил»). * Политика слабых паролей: настройка `password_policy` в `aa_settings()` (и в разделе `security` конфига). Слабым считается пароль из списка `aa_common_passwords()`, совпадающий с логином без учёта регистра или состоящий из одного повторяющегося символа. Режимы: `"off"` не проверять, `"warn"` (по умолчанию) принять пароль и показать предупреждение, `"reject"` отклонить пароль ошибкой `appauth_error_user` с причиной `password_common`, `password_equals_login` или `password_repeated`. В режиме `"warn"` модули показывают уведомление после добавления пользователя, сброса и смены пароля, при создании первого администратора и обязательной смене пароля и отправляют новое событие `weak_password_set` (значение: «логин: причина»). Новые тексты `password_common`, `password_equals_login`, `password_repeated`, `weak_password_notice`.
* `aa_event_logger()`: готовый обработчик событий для `on_event`. Приложение задаёт только функцию записи `writer(action, user, session_id, value)`; пакет берёт на себя отбор событий (`events`, `actions`), переименование в названия действий журнала (`actions`), включение и выключение записи по событию (`enabled`, функция вызывается при каждом событии, поэтому изменения конфига действуют сразу) и преобразование значения (`format_value`). Опечатки в названиях событий ловятся сразу, сбой записи не прерывает действие пакета.
* Удаление пользователя в `aa_users_server()` требует подтверждения: кнопка «Удалить аккаунт» открывает окно с кнопками «Да, удалить» и «Отмена». Сервер удаляет только того пользователя, для которого показано окно, и только после нажатия кнопки подтверждения; подделанное или повторное подтверждение ничего не удаляет. Новые тексты `delete_confirm_title`, `delete_confirm_text`, `delete_confirm_button`, `button_cancel`. Идентификаторы для тестов: `delete_cancel`, `delete_confirm` (ID `delete` теперь только открывает окно).
